# 自主控制写字机的主要流程与难点

来源：`字幕.srt`  
整理目标：提取从普通写字机升级为“自主写字/自动写作业机器人”的核心实现流程、关键模块和主要难点。

## 一句话结论

字幕中描述的系统不是简单地把一段文字发给写字机，而是构建了一条完整自动化流水线：

```text
摄像头采集页面
-> 图像裁剪与版面识别
-> 找出题目和可填写区域
-> 多模态大模型答题
-> 文本/公式转手写笔迹
-> 像素坐标映射到机器物理坐标
-> 生成写字路径
-> 控制写字机执行
-> 翻页、压平、继续下一页
```

结合本项目已抓到的串口协议，底层执行层可以落到 GRBL/G-code：`G0` 空走、`G1` 写字轨迹、`M3S1000` 落笔、`M5` 抬笔、`G4 P0.2` 等待机械动作稳定。

## 主要流程

### 1. 页面采集

系统首先用摄像头拍摄作业页面。字幕里提到后期升级为工控摄像头，并加入稳定补光：

- 使用高质量相机获取整页图像
- 使用固定光照环境减少噪点
- 固定相机参数，避免每次临时调整 ISO、快门
- 将页面图像作为后续识别、定位、答题的输入

这一步的目标不是“拍清楚”这么简单，而是要让图像稳定到可以做坐标映射和版面识别。

### 2. 图像裁剪与预处理

拍下作业照片后，需要先裁剪、矫正、清理成便于算法处理的格式。

典型任务：

- 裁掉无关背景
- 校正文档透视和旋转
- 统一图像尺寸、方向、亮度
- 为版面识别模型准备输入

这一步如果不稳定，后面的题框、空格、坐标映射都会跟着漂。

### 3. 版面理解：识别题目和空白区域

字幕中使用 `LayoutLM` 做版面识别。它会结合文字内容和文字位置，识别出：

- 哪些区域是题目
- 哪些区域是需要填写的空
- 每一道题对应哪些填写位置
- 每个填写位置在图像上的像素坐标

字幕里明确提到，需要人工标注数据来训练模型：标出“哪里是题、哪里是空”，再针对作业场景微调。训练成本并不低，使用 RTX6000 48GB 显存跑了两天半；训练完成后，部署到 RTX4070 笔记本上推理，每页大约两秒多能输出框选结果。

### 4. 题目拆分与答题

识别出题目区域后，系统会把每道题交给多模态大模型作答。字幕中最终选择了云侧 `GPT-4o`，原因是综合准确率最高。

答题流程大致是：

- 将题目截图或裁剪区域提交给多模态模型
- 让模型理解题干、选项、空格、上下文
- 返回答案文本
- 对特殊题型调整 prompt，例如理科大题要求输出详细推导过程

字幕里还提到做过模型横评。最初用简单程序比对答案时评分偏低，因为模型可能输出解释，或者填空答案语义正确但文本不完全一致。后来改为让 AI 做柔性评分，再针对 GPT-4o 优化。

### 5. 提升答题准确率

字幕中总结了三种优化方式：

| 方法 | 作用 |
|---|---|
| 思维链/分步推导 | 让模型先列解题思路，再输出答案，提高复杂题正确率 |
| 联网搜索 | 让模型提取关键词查资料，适合知识性题目 |
| 告知空格数量 | 避免模型看漏空，特别是填空题中“5 个空只写 4 个答案”的错位问题 |

其中“空格数量”来自前面的 `LayoutLM` 版面识别结果。这个细节很关键：视觉模型不只给坐标，也给大模型提供结构化约束。

### 6. 文本转手写笔迹

大模型输出的是文本，但写字机需要的是笔尖路径。

字幕中提到一个关键坑：电脑字体本质上是闭合矢量轮廓，直接让机械臂描轮廓，会写成“空心字”。因此需要把字体变成类似人手写的单线笔画。

字幕中的处理路线：

```text
答案文本
-> 使用 handright 等工具渲染为带随机扰动的手写风格像素图
-> 对像素图做骨架化
-> 从骨架中提取笔画
-> 简化笔画路径
-> 得到可执行的写字轨迹
```

`handright` 的作用是基于字体渲染手写效果，并给闭合图形做随机偏移，让同一个字每次略有不同，更像人写的。

### 7. 数学公式与特殊格式处理

数学公式不能只按普通文本处理。字幕中提到，大模型输出的公式通常是 `LaTeX` 格式，因此需要额外流程：

```text
LaTeX 公式
-> LaTeX 引擎渲染成像素图
-> 骨架化
-> 提取笔画
-> 转换为机械臂路径
```

作文、方格纸、特殊答题卡也需要定制算法。例如语文作文要写在格子里，就要识别格子，并按格子逐字排版。

### 8. 坐标标定：像素坐标到物理坐标

视觉系统得到的是像素坐标，但写字机执行的是物理坐标，通常是毫米。

字幕中采用的是仿射变换：

- 在纸面或工作区定义若干校准点
- 让机械臂画出二维码或标记点
- 相机识别这些点的像素位置
- 解出像素坐标系到机器坐标系的映射
- 后续所有题框、空格、笔画路径都通过该映射转成物理坐标

这一步是自主控制写字机的分水岭。没有稳定标定，只能“在大概位置写”；有了标定，才能“想在哪儿写就在哪儿写”。

### 9. 轨迹生成与写字机执行

最终系统需要把笔画路径发送给写字机。

结合本项目抓包结果，底层可采用 GRBL/G-code 控制：

```gcode
G21
G90
G0 X10Y10F2500
M3S1000
G4 P0.2
G1 X20Y10F1500
G1 X20Y20F1500
M5
G4 P0.2
```

推荐执行模型：

- 每段笔画前用 `G0` 空走到起点
- 用 `M3S1000` 落笔
- 用 `G4 P0.2` 等待落笔稳定
- 连续发送 `G1` 写出笔画轨迹
- 用 `M5` 抬笔
- 用 `G4 P0.2` 等待抬笔稳定
- 按 `ok` 应答做串口流控，避免塞爆 GRBL 缓冲区

### 10. 翻页与连续执行

字幕中从“写单页”升级到“写一本作业”的关键是翻页机构。

尝试过的方案：

| 方案 | 问题 |
|---|---|
| 滚轮翻页 | 纸页贴得紧，容易一次翻多页 |
| 真空吸盘 | 作业纸太薄，不容易安全吸起，结构也复杂 |
| 风扇/涵道电机吸页 | 通过气流把单页吸起，再由机械结构拉过来，最终可用 |

最终 2.0 版本使用高速涵道电机和专门设计的风道，通过高速气流制造压力差来吸起书页。翻页后还要压平页面，再继续拍照、识别、答题、写字。

## 主要难点

### 难点 1：普通写字机只能“预编程写字”

普通写字机通常只能把软件给定的文字写在固定位置。要实现自主控制，必须补齐：

- 页面感知
- 题目理解
- 答案生成
- 位置定位
- 轨迹生成
- 连续翻页

它不再是“写字机软件”，而是一个视觉、AI、运动控制串起来的闭环自动化系统。

### 难点 2：机械结构稳定性

字幕里 1.0 基于现成写字机改装，暴露了明显问题：

- 3D 打印件外挂翻页结构，强度差
- 运动时抖动大
- 滑轮车结构精度低
- 橡胶轮不圆或轨道不平都会引起震动
- 工具头太重，速度慢且稳定性差

2.0 的解决方向：

- 写字头和翻页头分离
- 两层结构，各自独立运动
- 使用线轨提高直线运动精度
- 使用 CoreXY 结构，让电机固定不参与运动
- 用自行车刹车线做落笔机构，减轻工具头重量
- 润滑线轨和轴承，提高运动平顺度

### 难点 3：版面识别不是 OCR 那么简单

只识别文字还不够，系统必须理解“结构”：

- 哪些文字属于题干
- 哪些区域是答案空
- 一个题对应几个空
- 每个空的位置和尺寸
- 多题、多栏、表格、选择题、填空题如何归属

这也是为什么字幕中选择 `LayoutLM`，而不是只用普通 OCR。

### 难点 4：大模型答题准确率有限

字幕里多次提到，模型不是稳定满分：

- 多模态模型看图答题不如纯文本版本稳定
- 数学、理科推理容易错
- 选择题可能输出解释，导致自动评分困难
- 填空题可能语义对但文本不一致
- 多空题容易漏空或错位
- 大题需要专门 prompt 才能写出过程

字幕中的优化后准确率达到约 `74.4%`，但仍有明显长尾问题。

### 难点 5：文本到笔迹的转换

机械臂不能直接写“字体文件”。字体通常是闭合轮廓，直接描会变成空心字。

真正可写的路径需要解决：

- 字体渲染
- 手写随机性
- 像素图骨架化
- 笔画顺序推断
- 笔画简化
- 笔画之间抬笔/落笔
- 不同字体、中文、英文、数字的统一处理

这一步是写字效果像不像人的关键。

### 难点 6：公式、作文、格子等特殊格式

数学公式涉及 `LaTeX` 渲染和符号排版，字幕中也提到数学题的主要问题之一就是 LaTeX 格式和渲染。

特殊格式包括：

- 上标、下标、分式、角度符号
- 方格作文纸
- 大题分步推导
- 选择题只写选项
- 填空题答案长度超过空格

这些都不能只靠通用文本渲染解决，需要按题型做规则或专门算法。

### 难点 7：像素坐标与机器坐标的标定

相机看到的是像素，写字机执行的是毫米。中间必须有稳定的几何映射。

主要风险：

- 相机位置变化导致映射失效
- 页面倾斜或翻页后位置变化
- 纸张隆起导致局部坐标不准
- 书本中缝区域高度变化，笔可能划过页面

字幕中使用仿射变换和校准点解决平面映射，但实际书页并不总是完美平面，这是后续精度瓶颈。

### 难点 8：翻页和压平

翻页不是“把纸翻过去”这么简单，还要保证：

- 一次只翻一页
- 不撕纸、不卷纸
- 翻页后页面位置可预测
- 书页能压平
- 中缝隆起不会影响书写

字幕中后期发现，中间隆起会让笔划出不该有的印子。解决办法是：

- 调整压平机构位置，压住中间隆起
- 规划笔的移动路径，跨页或换区域时绕开隆起处

### 难点 9：效率与缓存控制

字幕中完整写完 44 页耗时 3 小时，而且是在“大题不多”的情况下。影响效率的因素包括：

- 页面识别推理耗时
- 云端大模型答题延迟
- 笔迹生成耗时
- 写字机物理速度
- 落笔/抬笔等待
- 翻页和压平动作
- 串口流控和 GRBL 缓冲区限制

如果基于本项目的 GRBL 串口协议实现自主控制，建议初期采用“一条命令等待一个 `ok`”的保守模式；稳定后再实现 GRBL streaming buffer，提高吞吐。

## 面向本项目的落地架构建议

结合现有 `serial_proxy.py` 和 `protocol_analysis.md`，可以把项目拆成以下模块：

```text
camera_capture.py        # 拍照、裁剪、透视校正
layout_detect.py         # OCR/LayoutLM，输出题目框和答案框
answer_solver.py         # 调用多模态模型，输出结构化答案
handwriting_render.py    # 文本/公式转像素图，再骨架化成笔画
coordinate_mapper.py     # 像素坐标 -> 机器毫米坐标
gcode_generator.py       # 笔画路径 -> G-code
grbl_sender.py           # 串口发送、等待 ok、暂停/终止/恢复
page_turner.py           # 翻页、压平、避开中缝路径
main_pipeline.py         # 串起整页/整本作业流程
```

结构化数据建议：

```text
PageImage
-> LayoutRegion[]
-> Question{image, answer_boxes, type}
-> Answer{text, latex?, steps?}
-> StrokePath[]
-> GCodeJob
```

## 最小可行版本建议

先不要一口吃成“自动写完整本作业”。比较稳的路线是：

1. 先手动指定一个写字区域，输入文字，生成 G-code 写出来
2. 加入像素坐标到机器坐标的标定
3. 拍照后手动框选答案区域，让系统自动写到指定位置
4. 加 OCR/LayoutLM 自动识别空格
5. 加大模型答题
6. 加文本转手写骨架化
7. 最后再做翻页、压平和整本循环

这样每一步都有独立可验证的输出，不会把视觉、AI、运动控制、机械翻页全搅在一起调。

## 与当前串口抓包的对应关系

当前已知写字机底层命令足够支撑自主控制：

| 上层动作 | 底层 G-code/GRBL |
|---|---|
| 设置工作零点 | `G10 P0 L20 X0Y0Z0` |
| 使用毫米单位 | `G21` |
| 绝对坐标 | `G90` |
| 抬笔空走 | `G0 X...Y...F2500` |
| 落笔 | `M3S1000` |
| 写字轨迹 | `G1 X...Y...F1500` |
| 抬笔 | `M5` |
| 等待动作稳定 | `G4 P0.2` |
| 回原点 | `G90G0 X0Y0` |
| 软复位 | `0x18` |

也就是说，本项目后续的核心不是“破解协议”了，而是把视觉识别和笔迹路径正确转成这些 G-code 命令。
