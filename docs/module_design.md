# 写字机自主控制项目模块设计

## 总体原则

项目建议拆成“图像准备 -> 字迹定位 -> 笔迹矢量化 -> 文本生成辅助 -> 机器执行”五层。

关键边界：

- 模块 1 负责生成标准化底图坐标系。
- 模块 2 负责让用户把答案图片对齐到底图坐标系，并输出透明字迹合成图。
- 模块 3 负责把黑色字迹像素图转换成像素坐标下的笔画轨迹。
- 模块 4 只负责把文本生成手写风格像素图，是模块 2 的输入辅助工具。
- 模块 5 负责把像素轨迹转换成机器物理坐标和 G-code，并通过串口控制写字机。

因此，“根据底图实际物理尺寸与像素尺寸，把字迹位置变成可执行写字轨迹”更适合放在模块 5。模块 3 不应该知道串口、毫米、GRBL、落笔抬笔这些机器细节，只输出和底图同坐标系的抽象笔画路径。

## 数据流

```text
手机拍摄作业纸照片
-> 模块 1：参考底图设置
-> 标准底图 image + physical_size_mm + pixel_size

答案截图/扫描图/文本生成图
-> 模块 2：手动字迹定位
-> 融合后的透明字迹图 alpha handwriting image

透明字迹图
-> 模块 3：骨架提取与笔顺优化
-> 像素坐标笔画 StrokePath[]

StrokePath[] + 底图尺寸信息
-> 模块 5：执行器
-> 毫米坐标轨迹 + G-code + 串口执行
```

模块 4 是旁路辅助：

```text
文本
-> 模块 4：Handright 文本笔迹转换
-> 手写像素图
-> 导入模块 2 继续定位
```

## 模块 1：参考底图设置模块

### 目标

把用户手机拍的作业纸照片变成一个标准正视图底图，并建立像素尺寸和真实物理尺寸的关系。

### 用户操作

1. 导入手机拍摄的作业纸照片。
2. 手动点选四个角点。
3. 可进行旋转、翻转等操作。
4. 输入真实宽高，单位 mm。
5. 确认后执行透视变换。

### 关键设计

输出目标像素尺寸：

```text
target_width_px = width_mm * 10
target_height_px = height_mm * 10
```

也就是 `10 px/mm`，等价于 `0.1 mm/px`。这个精度对普通写字机来说比较舒服，既不会太粗，也不会让路径点数量爆炸。

### 角点同步

用户对原图做旋转、翻转时，已经选取的角点必须同步变换。建议内部始终维护角点在当前显示图像坐标系下的位置，而不是每次重新从原图推断。

需要支持：

- 90 度旋转
- 水平翻转
- 垂直翻转
- 角点拖拽微调
- 角点顺序校验

### 角点顺序建议

统一使用：

```text
top_left
top_right
bottom_right
bottom_left
```

确认前做一次顺序和几何合法性检查：

- 四边形不能自交
- 面积不能过小
- 点位顺序不能绕反
- 长宽比例和用户输入的物理尺寸不能差异过大

### 输出

```text
ReferenceCanvas {
  background_image: 标准透视变换后的底图
  width_mm: float
  height_mm: float
  width_px: int
  height_px: int
  px_per_mm: 10
}
```

## 模块 2：手动字迹定位模块

### 目标

让用户把包含答案的图片手动对齐到底图上，并只保留黑色字迹，最终输出一张和底图尺寸完全一致的透明字迹图。

### 设计定位

底图只用于辅助定位，不参与最终融合。最终融合图只包含用户导入的答案字迹。

### 用户操作

1. 自动载入模块 1 的底图作为预览背景。
2. 用户导入一张包含答案的图片。
3. 对该图片进行裁剪、旋转、缩放、平移。
4. 支持无级小角度旋转。
5. 确认后，自动抠出黑色字迹，其余区域透明。
6. 用户可以继续导入更多答案图片。
7. 所有答案图层确认后，融合成一张透明字迹图。

### 图层模型

建议把每个导入图片当作一个独立图层：

```text
AnswerLayer {
  source_image
  crop_rect
  transform {
    x
    y
    scale
    rotation_deg
  }
  black_extract_params {
    threshold
    denoise
    alpha_smooth
  }
}
```

这样用户可以随时返回修改某一层，而不是每确认一次就不可逆地烙到画布上。

### 黑色字迹提取

基础方法：

```text
RGB/HSV/灰度
-> 判断深色像素
-> 生成 alpha mask
-> 去除背景
-> 输出 RGBA
```

建议提供可调参数：

- 黑色阈值
- 去噪强度
- 最小连通域面积
- 笔迹膨胀/腐蚀
- 透明边缘平滑

因为不同照片里“黑字”可能是灰黑、蓝黑、阴影黑，这里完全自动会比较脆，给用户一个阈值滑杆很值。

### 输出

```text
handwriting_merged.png
```

要求：

- 尺寸与底图完全一致。
- 背景透明。
- 只包含用户导入的答案字迹。
- 字迹位置与用户预览时一致。

## 模块 3：字迹生成模块

### 目标

把模块 2 输出的透明字迹图转换成可执行的抽象笔画轨迹。

注意：这里的“可执行”是指逻辑上可写，不是机器层面的 G-code。模块 3 输出仍然是像素坐标。

### 输入

```text
handwriting_merged.png
```

### 处理流程

```text
透明字迹图
-> 二值化
-> 去噪
-> 骨架提取
-> 连通域分析
-> 端点/交叉点识别
-> 笔画拆分
-> 笔顺优化
-> 路径简化
-> 输出 StrokePath[]
```

### 难点

- 骨架可能有毛刺。
- 字迹断裂会导致一笔被拆成多笔。
- 字迹粘连会导致多个字混在一起。
- 自动笔顺不一定符合人类习惯。
- 路径点太密会拖慢串口和机器执行。
- 路径点太稀会导致字形变形。

### 输出建议

```json
{
  "coordinate_space": "reference_canvas_pixel",
  "width_px": 2100,
  "height_px": 2970,
  "strokes": [
    {
      "points": [[100, 120], [101, 121], [105, 126]],
      "closed": false
    }
  ]
}
```

### 路径优化建议

使用 Ramer-Douglas-Peucker 或类似算法做路径简化，并设置毫米级误差，例如：

```text
epsilon_px = 1~3 px
```

在 `10 px/mm` 下，相当于 `0.1~0.3 mm` 误差。

## 模块 4：文本笔迹转换模块

### 目标

让用户输入文本，自动生成手写风格像素图，供模块 2 继续定位。

### 技术路线

使用：

```text
github.com/Gsllchb/Handright
```

### 模块定位

模块 4 不直接控制写字机，也不直接输出 G-code。它只是一个“答案图片生成器”。

原因：

- 用户可能自己用截图、扫描、别的软件生成答案图。
- Handright 生成的图还需要对齐到作业纸空格中。
- 同一段文本可能要裁切、缩放、旋转后才能写到合适位置。

所以模块 4 的输出应该回流到模块 2。

### 输出

```text
handright_output.png
```

背景建议透明，或者至少支持后续模块 2 自动抠黑字。

## 模块 5：执行器

### 目标

连接写字机，将模块 3 输出的像素轨迹转换为实际机器坐标和 G-code，并负责开始、暂停、继续、终止。

### 为什么物理轨迹转换放在模块 5

模块 3 只知道“在底图第几个像素处有一条笔画”。  
模块 5 才知道：

- 真实宽高是多少 mm
- 每个像素对应多少 mm
- 写字机原点在哪里
- X/Y 轴方向是否需要翻转
- 空走速度、写字速度是多少
- 落笔/抬笔命令是什么
- 串口如何等待 `ok`
- 暂停和终止如何处理

因此像素轨迹到机器轨迹、G-code 生成、串口发送都应该归执行器模块。

### 输入

```text
ReferenceCanvas
StrokePath[]
MachineConfig
```

### 机器配置

```text
MachineConfig {
  port: COM3
  baud: 115200
  origin_x_mm: 0
  origin_y_mm: 0
  invert_x: false
  invert_y: false
  travel_feed: 2500
  write_feed: 1500
  pen_down: "M3S1000"
  pen_up: "M5"
  dwell_seconds: 0.2
}
```

### 像素到毫米

模块 1 固定 `10 px/mm` 时：

```text
x_mm = x_px / 10
y_mm = y_px / 10
```

如果机器坐标方向和图像坐标方向不同，则在模块 5 里处理：

```text
if invert_x:
  x_mm = width_mm - x_mm

if invert_y:
  y_mm = height_mm - y_mm
```

### G-code 生成

每一条 stroke 建议转换为：

```gcode
G0 X{start_x}Y{start_y}F2500
M3S1000
G4 P0.2
G1 X{x1}Y{y1}F1500
G1 X{x2}Y{y2}F1500
...
M5
G4 P0.2
```

初始化建议：

```gcode
G21
G90
M5
```

可选设置工作零点：

```gcode
G10 P0 L20 X0Y0Z0
```

结束建议：

```gcode
M5
G90G0 X0Y0
```

### 串口执行

结合当前抓包结果：

- 波特率：115200
- 固件：GRBL 1.1f
- 命令以 `\n` 结尾
- 设备返回 `ok\r\n`

初期建议一条命令等待一个 `ok`。稳定后再做 GRBL streaming buffer。

### 暂停

建议分两级：

1. 软件暂停：停止继续发送新 G-code，等待当前命令完成后发送 `M5` 抬笔。
2. GRBL feed hold：发送 `!`，让 GRBL 立即暂停运动。

从前一次抓包看，官方软件暂停更像是停止继续下发并发送 `M5`，没有明确看到 `!` 和 `~`。因此第一版建议先做软件暂停，更可控。

### 继续

软件暂停后的继续：

- 如果只是停止发送新命令，则从当前 stroke 或下一条命令继续。
- 如果发送了 `!`，则需要发送 `~` 恢复 GRBL cycle start。

### 终止

终止建议：

```text
停止发送队列
发送 M5 抬笔
可选发送 0x18 soft reset
可选回原点 G90G0 X0Y0
```

如果机器正在运动中，最安全的终止策略通常是：

1. 发送 `!` 暂停。
2. 发送 `M5` 或 reset 后保证抬笔。
3. 清理软件队列。
4. 用户确认后再回原点。

## 推荐开发顺序

1. 实现模块 1：底图透视校正和物理尺寸输入。
2. 实现模块 2：图片图层定位、抠黑字、合成透明图。
3. 实现模块 5 的最小版：手写几条测试 G-code，确认机器坐标方向。
4. 实现模块 3：从合成图生成 StrokePath。
5. 打通模块 3 -> 模块 5：把 StrokePath 写出来。
6. 接入模块 4：文本生成手写图，再走模块 2。
7. 优化暂停、终止、路径简化、笔顺和 UI 操作体验。

先做模块 5 的最小版是为了尽早确认机器坐标、方向、速度和落笔抬笔行为。否则前面图像流程做得再漂亮，最后可能发现机器坐标系和预期相反，那就有点像把地图画完才发现北在脚底，挺刺激但不划算。

## 文件产物建议

```text
project.json                         # 项目配置，记录底图、物理尺寸、图层、机器配置
reference_canvas.png                 # 模块 1 输出的标准底图
handwriting_merged.png               # 模块 2 输出的透明字迹图
strokes.json                         # 模块 3 输出的像素轨迹
job.gcode                            # 模块 5 输出的 G-code
execution_log.txt                    # 串口执行日志
```

## 最重要的接口约定

模块之间不要互相吃掉对方的职责。

最关键的两个接口：

```text
模块 2 -> 模块 3:
一张与底图同尺寸的透明字迹 PNG
```

```text
模块 3 -> 模块 5:
底图像素坐标系下的 StrokePath[]
```

只要这两个接口稳定，后面 UI、算法、写字机型号都可以独立替换。
